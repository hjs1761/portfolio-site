## 한눈에

사내에 흩어진 “왜 그렇게 했는지”를 근거 타임라인과 원본 링크로 답하는 검색입니다. 현재 **사내 파일럿 운영 중 · 전사 오픈 전**이며, 지정된 사무실 기기 안에서만 접속할 수 있습니다. 설계·판단·검증·운영은 제가 맡았고, Python 코드 구현은 AI 코딩 에이전트 **Claude Code**가 담당했습니다.

## 왜 만들었나

기능이 만들어진 이유는 요청 글 하나에 담기지 않습니다. 업무 본문, 댓글, 회신 메일, 메신저를 날짜순으로 이어 읽어야 결정의 배경이 보입니다. 담당자가 바뀌면 이 과정을 다시 수행하기도 어렵습니다.

이 기록을 모아 요약하되, 사용자가 판단의 근거를 직접 확인하게 만들고자 했습니다. 그래서 핵심 화면을 채팅창보다 **근거 타임라인**으로 정했습니다. 실제 질문의 정답이 오래된 업무에 있었으므로 최근 기간만 수집하지 않고 전량 적재했습니다.

기준은 세 가지였습니다. 두레이에서 볼 수 없는 자료는 여기서도 볼 수 없어야 합니다. 근거가 없으면 찾지 못했다고 답해야 합니다. 원본은 고치지 않고, 처리 규칙이 바뀌면 원본에서 다시 만들어야 합니다.

## 구성

1. **출처**  
   두레이 업무·댓글·위키·메일·메신저와 사내 GitLab의 코드·변경 기록을 대상으로 합니다. 언어 모델과 기록 서버도 사내에서 실행합니다.

2. **수집**  
   업무와 대화방은 신청자 본인의 접근 권한으로 API에서 증분 수집합니다. API로 받지 못하는 메일과 메신저 과거분은 관리자 수동 수집이나 설치 앱으로 보완합니다.

3. **정규화**  
   원본을 별도로 보관하고, 인용·서명·첨부 잔여물을 정리합니다. 메일은 스레드별 대화로 묶고, 메신저는 업무 기록으로 정리한 내용만 후속 단계에 넘깁니다.

4. **청킹**  
   일반 문서는 길이를 기준으로 나누고 짧은 꼬리는 앞에 붙입니다. 메일은 한 통씩, 코드는 함수·클래스별로 나누며 제목과 프로젝트 맥락을 붙여 임베딩합니다.

5. **임베딩·색인**  
   bge-m3 벡터를 PostgreSQL의 pgvector HNSW 인덱스에 저장합니다. 코드·번호는 별도 텍스트 정확 일치 경로로 보완하고, 인덱스는 버전별로 만듭니다.

6. **권한**  
   문서의 리소스 권한과 사용자의 멤버십을 검색 쿼리에서 대조합니다. 권한 없는 문서는 검색 후보에도 들어오지 않습니다.

7. **검색 흐름**  
   LangGraph 하나에서 검색, 답변 생성, 판정을 연결합니다. 의미 검색과 정확 일치 후보를 리랭킹하고, 사람·최근성 조건을 반영해 답변·못 찾음·되묻기를 결정합니다.

8. **답변**  
   근거를 모델에 전달하고 문장마다 근거 번호를 붙입니다. 근거 밖의 날짜·이름·수치를 만들지 않으며, 예정이나 요청을 완료된 결과로 바꾸지 않게 했습니다.

9. **기록**  
   사내 Langfuse에 검색어·순위·답변·지연 시간·피드백을 연결합니다. 민감한 호출은 기록에서 제외하고, 기록 장애가 답변을 막지 않게 했습니다.

## 설계 결정

### 근거 중심 화면과 직접 구성한 검색

- **결정**: 수집기·검색 API·화면은 프로젝트에 맞게 만들고, 모델 서빙은 OpenAI 호환 기성품을 사용했습니다.
- **이유**: 한국어 청킹, 권한 필터, 평가 과정을 직접 확인하고 바꿀 수 있어야 했습니다. 화면에서는 근거가 가장 먼저 보여야 했습니다.
- **대안**: 올인원 플랫폼은 추상화와 워크스페이스 단위 권한이 제약이었습니다. 기성 채팅 화면은 근거를 각주로 접었습니다. 모델 서빙까지 직접 만들 필요는 없었습니다.
- **결과**: 개인 장비 의존을 없애고 사내 모델 서버로 이전했습니다. 이전 시 평가 문턱 네 개를 모두 통과했습니다.

### 못 찾음 판정에 리랭커 사용

- **결정**: 리랭커가 정상 실행됐을 때 그 점수로 답할 근거가 있는지 판단합니다.
- **이유**: dense 검색의 최고 점수 분포가 답이 있는 질문과 없는 질문에서 겹쳤습니다. 유사도만으로는 답변 가능 여부를 가르기 어려웠습니다.
- **대안**: dense 점수 기준은 리랭커 장애 시 대비책으로 남겼습니다.
- **결과**: 도입 직후 ‘못 찾았다’ 지표가 0.000에서 0.500으로 올랐습니다. 이후 제거 실험에서는 MRR이 0.829에서 0.741로, ‘못 찾았다’가 0.800에서 0.200으로 떨어졌습니다.

### 평가를 통과한 인덱스만 활성화

- **결정**: `build → eval → activate` 순서를 고정하고, 자동 동기화에도 변경 감지 게이트를 뒀습니다.
- **이유**: 자동 수집이 평가 없이 새 메일을 운영 인덱스에 넣어 MRR이 크게 떨어진 사고가 있었습니다.
- **결과**: 새 소스 종류는 보류하고 청킹 코드 지문이 달라지면 동기화를 멈춥니다. 반송 알림 제외 규칙을 바꿨을 때 실제로 멈췄다가 새 인덱스 활성화 후 재개했습니다. 직전 운영 버전으로 되돌릴 수도 있습니다.

### 권한을 검색 후보 단계에서 적용

- **결정**: 문서의 리소스 목록과 사용자 멤버십을 분리하고, 검색 쿼리에서 권한을 적용합니다.
- **이유**: 멤버가 바뀔 때 청크를 다시 만들지 않고 권한만 갱신할 수 있습니다. 프로젝트 밖의 대화방·위키·업로드 권한도 표현해야 했습니다.
- **결과**: 권한 누출 0건을 반영 조건으로 삼았습니다. 저장소 명단에 없는 계정으로 코드 근거가 나오지 않는지도 별도로 검증했습니다. 관리자도 저장소 명단에 있어야 검색할 수 있습니다.

### 메신저는 업무 정리본만 사용

- **결정**: 메신저의 색인·답변·화면은 모두 같은 업무 정리본을 봅니다. 정리본이 없으면 문서를 만들지 않습니다.
- **이유**: 대화 전체를 근거로 보여 주면 감정 표현과 잡담도 노출됩니다. 답변이 화면에 없는 원문을 인용해서도 안 됩니다.
- **대안**: 정리 실패 때 원문으로 대체하는 방식은 채택하지 않았습니다.
- **결과**: 비밀 가림과 주제 판정을 정리보다 먼저 수행합니다. 정리 과정의 환각 위험은 남아 있어 프롬프트 제약과 이름 검사로 확인합니다.

### 메일은 스레드로 묶고 한 통씩 나누기

- **결정**: 문서는 스레드 단위로 만들되, 색인할 조각은 한 통씩 나눴습니다.
- **이유**: 메일마다 문서를 만들면 회신 인용이 반복돼 같은 스레드가 검색 상위를 채웠습니다.
- **대안**: 통 단위 문서 색인은 MRR이 0.902에서 0.419로 떨어져 되돌렸습니다. 스레드 단위로 바꾸자 0.718로 회복했습니다.
- **결과**: 후속 청킹 실험에서 MRR은 0.722에서 0.829로 올랐습니다. 다만 “긴 청크에 항의 문장이 묻힌다”는 원래 가설은 반증됐고 목표 질문은 나빠졌습니다. ‘못 찾았다’도 1.000에서 0.800으로 내려갔습니다. 주제어가 분명한 질문의 개선과 악화 문항의 답변 내용을 검토해 채택했습니다.

### 화면과 평가를 LangGraph 하나로 통일

- **결정**: 자체 검색 부품을 LangGraph 노드로 감싸고, 화면과 평가가 같은 그래프를 실행하게 했습니다.
- **이유**: 별도 경로에서 표집 설정·못 찾음·되묻기 판정이 달라지는 버그가 있었습니다. 이후 여러 단계 검색을 붙일 구조도 필요했습니다.
- **대안**: 현재 흐름은 일반 함수로도 가능하지만 확장 경로를 고려해 그래프로 옮겼습니다. LangChain 부품은 사용하지 않았습니다.
- **결과**: 이전 전후 평가 34문항의 판정이 같았습니다. LangSmith 추적은 강제로 끄고 실제 요청의 연결 대상도 확인했습니다.

### 관측 기록도 사내 권한 문제로 취급

- **결정**: Langfuse를 사내에 설치하고 파일럿 동안 관리자만 열람하게 했습니다.
- **이유**: 이상 답변 제보를 DB 조회와 재현만으로 추적하기 어려웠습니다. 동시에 관측 화면에서는 여러 사용자의 질문과 검색 근거를 함께 볼 수 있다는 문제가 있었습니다.
- **대안**: LangSmith는 외부 전송 때문에 제외했습니다. Phoenix도 비교했으나 필요한 기능과 사용 사례를 고려해 Langfuse를 선택했습니다.
- **결과**: 질문부터 판정까지 연결해 볼 수 있게 했습니다. 기록은 30일 후 정리하며, 전사 확대 전에는 본문 기록을 끌 계획입니다.

## 품질을 재는 방법

업무 검색 평가셋은 **77문항, 공개 62문항과 봉인 15문항**입니다. 저장소 검색은 별도 15문항으로 평가합니다. 정답 문서는 제가 두레이에서 직접 찾아 정했습니다. 시스템이 이미 찾은 결과를 정답으로 삼지 않았고, 봉인 문항은 튜닝에 쓰지 않습니다.

Recall@10은 상위 검색 결과에 정답이 있는지, MRR은 정답이 얼마나 앞에 있는지 봅니다. 답변 정답률과 답이 없는 질문에서의 ‘못 찾았다’ 지표도 따로 확인합니다. 평가 판정에 LLM-as-judge는 쓰지 않습니다.

인덱스 교체 문턱은 **Recall@10 ≥ 0.8, ‘못 찾았다’ ≥ 0.8, 권한 누출 0건, 되묻기 남용 0건**입니다. 코드 RAG에는 카드 검증 통과율 ≥ 0.9, 비밀값 노출 0건, 저장소 접근 권한이 없는 계정의 코드 근거 0건을 더했습니다.

측정 후 기각한 실험은 <strong>11건(2026-10-22 기준)</strong>입니다. 대표적으로 리랭커 후보를 40개에서 100개로 늘린 안은 일부 10문항에서는 좋아 보였습니다. 전체 53문항에서는 정답률이 0.857에서 0.643으로 떨어져 기각했습니다. 개발자 보기에서도 모델에 주는 코드 근거를 줄이자 못 찾음 판정이 무너졌습니다. 모델 입력은 유지하고 화면에서만 접도록 바꿨습니다.

측정 방법도 수정했습니다. 같은 질문을 반복한 속도 시험은 캐시 효과를 재고 있어 새 입력으로 한 번씩 측정했습니다. 동시 평가는 리랭커의 429 응답을 유발하므로 순차 실행합니다. 모델 출력과 자료 변화의 영향을 구분하려고 같은 시간대에 두 버전을 번갈아 평가합니다. 정답 인용만 맞고 내용은 틀린 답을 잡기 위해 핵심어 지표도 참고합니다.

‘최근’ 질문은 정답 문서를 고정하지 않고 평가 시점의 조건으로 계산합니다. 문항 구성이 달라진 날짜의 점수는 단순 비교하지 않습니다. 실제 질문이 늘면서 점수가 내려간 것도 이 구분 아래 해석했습니다.

리랭커가 조용히 꺼진 채 벡터 검색만 수행한 일은 세 번 있었습니다. 잘못된 상태 확인, 필수 모델 항목 누락, 일시 오류 뒤 영구 비활성화가 원인이었습니다. 기동 때 실제 호출과 경고를 추가하고, 실패 후 재시도와 429 대기를 넣었습니다. **실패하면 벡터 결과로 이어 가는 동작은 남아 있습니다.**

## 자동 수집과 동기화

승인된 소스는 5분마다 수집·정규화한 뒤 활성 인덱스에 갱신합니다. 새 소스 종류와 청킹 변경은 평가를 거치도록 멈춥니다. 저장소 종류는 별도 빌드·평가·활성화로만 반영합니다. 청킹 지문은 AST를 사용해 주석·서식 변경 때문에 불필요하게 멈추지 않게 했습니다.

관리자 일시정지, 중복 실행, 수집 환경 이상도 회차를 멈추는 조건입니다. 소스별 실패는 간격을 늘려 재시도하고, 반복 실패는 수동 확인으로 넘깁니다. 메신저 정리 모델이 연속 실패하면 해당 처리도 중단합니다.

사용자는 자신의 접근 권한으로 프로젝트·방 수집을 신청하고 관리자가 승인합니다. 다음 회차부터 신청자 기준으로 수집합니다. 이로써 관리자 한 사람의 권한과 코드 상수가 수집 범위를 정하던 구조를 바꿨습니다. 멤버십은 동기화마다 갱신하며, 접근권 상실이 확인된 리소스는 검색 권한을 비웁니다. 단순 통신 실패는 접근권 상실과 구분합니다.

개인 메일함은 프로젝트와 기간을 정한 뒤 머리글로 후보를 거르고, 사용자가 선택한 메일만 올립니다. 읽기 전용으로 연결해 읽음 상태를 바꾸지 않습니다. 웹과 설치 앱 경로는 구현됐지만 다른 PC에서 접속할 수 없어 실사용 전입니다. 공용 메일함과 메신저 과거분은 관리자 수동 수집이 남아 있습니다.

Electron 설치 앱에서는 사용자가 두레이 창에 직접 로그인합니다. 앱은 해당 세션으로 메일을 가져오며 서버는 제출 자료를 다시 검사합니다. 업로드 본문의 진위까지 확인할 수는 없어 출처 표시, 올린 사람 기록, 관리자 삭제로 대응합니다.

## 운영 서버·GitLab 자동 연동

운영 서버가 코드의 원본인 프로젝트에서는 서버에서 직접 고친 내용이 GitLab에 커밋되지 않아, 저장소만 검색하면 현재 동작을 설명하기 어려웠습니다. 운영 서버의 파일을 GitLab에 매일 남기고 검색으로 연결해, 현재 코드와 운영 변경 기록을 함께 읽도록 했습니다. 구현은 AI 코딩 에이전트 Claude Code가 맡았으며, 저는 설계·판단·검증·운영을 담당했습니다.

### 흐름

1. **연결 신청**: 운영 서버 연결 화면에서 FTP·SFTP 서버를 연결할 신청을 만듭니다. W_Archive는 신청 상태·화면·감사 기록을 맡고, 접속 비밀번호와 GitLab 쓰기 토큰은 prod-mirror만 보관합니다.
2. **관리자 승인과 첫 실행**: 승인 시 prod-mirror 판 번호와 W_Archive 검토 상태 지문을 함께 대조합니다. 받기 시험을 거쳐 GitLab 저장소를 만들고 첫 실행을 마치면 운영 대상으로 옮기며, W_Archive가 저장소를 검색 소스로 등록합니다.
3. **매일 동기화**: 00:30에 컨테이너가 대상 저장소를 fetch한 뒤, 제외 규칙과 파일 크기 상한을 통과한 서버 파일을 빈 임시 폴더로 받습니다. 서버는 읽기만 하며, 서버에서 삭제한 파일은 사본에서도 지웁니다. 받기에 실패한 출처는 지난 사본을 유지합니다.
4. **GitLab 봇 가지에 기록**: 변경이 있으면 봇 전용 가지 `prod-mirror`에 커밋·push합니다. 이 가지에는 운영 서버 사본이 쌓이며, 기본 가지와 비교해 서버에만 반영된 변경을 확인합니다.
5. **매일 밤 저장소 수집**: 검색 수집기가 야간 저장소 수집 회차에서 `prod-mirror`를 읽습니다. 저장소 자료는 빌드·평가·활성화를 거쳐 검색에 반영하며, 기능 카드·코드·변경 기록을 같은 인덱스에 넣습니다.
6. **코드 RAG의 두 가지 읽기**: 코드를 읽는 가지와 MR·커밋 이력을 읽는 가지를 따로 지정합니다. 운영 서버 사본은 `prod-mirror`에서, MR은 기본 가지에서 읽습니다. 코드는 git 추적 파일을 함수·클래스 단위로 나누고 GitLab 줄 범위 링크를 붙입니다.
7. **검색에서 변경 맥락 확인**: 현재 동작은 기능 카드와 코드로, 개발 과정의 맥락은 MR·이슈·커밋으로 설명합니다. 봇 커밋은 «운영에서 언제 무엇이 바뀌었나»를 확인하는 근거가 됩니다. 저장소 자료도 권한 필터를 거치며, 관리자 역시 접근 명단에 있어야 검색할 수 있습니다.

### 설계에서 정한 것

- **GitLab CI 예약 대신 별도 프로그램**: 제가 선택한 운영 방식입니다. 서버 파일을 받아 GitLab에 기록하는 일을 prod-mirror가 맡고, 검색 수집기는 그 저장소를 읽도록 책임을 나눴습니다. 현재 예약 실행은 컨테이너 daemon이 맡습니다.
- **파일 바이트와 비교 기준 보존**: 임시 색인으로 Git tree와 commit을 만들어 저장소의 줄바꿈 변환 설정에 영향을 받지 않게 했습니다. 기본 가지가 앞서 있으면 그 끝을 두 번째 부모로 연결해, GitLab 세 점 비교가 서버에서 직접 고친 내용을 보여 주도록 했습니다.
- **의심스러운 변경은 지난 사본을 유지하며 보류**: 새 경로의 비밀 설정·개인정보·바이너리와 기존 파일의 개인정보 급증은 커밋하지 않습니다. 실수로 올라온 파일을 잡기 위한 장치이며, 사람이 경로와 내용 지문을 확인한 뒤 받아들이도록 했습니다.
- **접속 자격과 git 실행 환경 분리**: 비밀번호와 쓰기 토큰을 prod-mirror에만 두고, git은 대상 저장소 토큰만 사용하게 했습니다. 전용 인증 도우미와 빈 전용 HOME을 사용해 기기의 git 설정이나 키체인에 의존하지 않도록 했습니다.
- **SFTP 우선과 FTP 경고 기록**: SFTP는 호스트 키를 고정합니다. 같은 서버에서 SFTP를 제공하면 이를 사용하고, 평문 FTP를 쓰는 경우에는 점검과 실행 회차 기록에 경고를 남겨 연결 방식의 제약을 드러냅니다.
- **승인 내용 대조와 외부 호출 복구**: 승인할 때 프로그램 판 번호와 검토 상태 지문을 모두 확인합니다. 외부 호출 전에는 기록을 먼저 확정하고, 결과를 알 수 없는 호출은 주기적으로 다시 확인해 신청 상태와 실제 처리 결과를 맞춥니다.
- **대상별 실패 격리와 중복 실행 방지**: 한 대상이 실패해도 다음 대상은 진행하고, 실패는 두레이로 알립니다. 컨테이너와 cron은 회차 잠금을 공유하지 않아 겹칠 수 있으므로 같은 기기에서 함께 사용하지 않습니다.
- **기능 카드의 근거 검사와 코드 전용 가리기**: 사람이 작성한 기능 목록에서 관련 코드·시험·변경 이력을 묶어 카드를 만들고, 모든 문장에 근거를 붙입니다. 인용 줄의 존재 여부와 문장별 근거를 기계·LLM으로 검사해 부정 판정 문장은 버립니다. 원문은 유지하고 검색 문서를 만들 때 가리되, 코드는 정상 구문을 훼손하지 않도록 비밀 형태만 가리고 줄 수를 보존합니다.

## 운영하며 겪은 문제

- **검색 결과가 빌드할수록 줄었습니다.** HNSW가 전체 버전에서 이웃을 찾은 뒤 버전 필터를 적용해 후보가 탈락했습니다. 탐색 범위를 늘리고 활성화 때 직전 운영 버전만 남기도록 정리했습니다.
- **정규화 규칙을 바꿔도 옛 문서가 남았습니다.** 새 결과만 갱신해 이전 산출물이 지워지지 않았습니다. 전량 정규화에서는 이번에 생성되지 않은 문서를 삭제하고, 증분 수집과 구분했습니다.
- **서명 연락처가 담당자 근거로 선택됐습니다.** 실제 참여자가 아닌 형식적 목록이었습니다. 도메인 확인을 거쳐 해당 처리를 되돌리고 업무 담당자 필드를 근거로 삼았습니다.
- **관리자가 보지 않은 변경이 승인될 수 있었습니다.** 운영 서버 연결 신청이 수정돼도 낡은 승인 화면이 통과할 여지가 있었습니다. 검토 상태를 함께 대조하고 화면이 확인한 상태를 유지하도록 수정했습니다.

## AI로 만드는 방식

먼저 설계 스펙·기능명세·화면설계·API·데이터 모델·평가셋을 문서 세트로 만들었습니다. 코드가 없는 상태에서 범위를 확정한 뒤 Claude Code에 구현을 맡겼습니다. 순서는 평가셋, 수집기, 청킹·인덱스, 검색과 평가, 답변, 화면이었습니다.

큰 기능은 설계와 작업 계획을 나누고, 작업마다 구현 후 계획 대조와 별도 품질·보안 검토를 진행했습니다. 문서와 구현이 다르면 문서를 기준으로 판단하고, 벗어나는 이유를 기록했습니다. 계획 자체에도 결함이 있어 계획대로 구현됐다는 사실만으로 승인하지 않았습니다.

별도 검토는 가짜 DB 시험이 놓친 SQL 타입·제약·경합 문제를 잡았습니다. 일회용 PostgreSQL 통합 시험을 추가하고, 설치 앱의 입력 검증 누락과 승인 상태 불일치도 수정했습니다. 검토자의 지적 역시 재현과 코드 확인을 거쳐 오판을 걸렀습니다.

제 몫은 정답과 도메인 판단, 실험 채택·기각, 모델 선택, 운영 순서 결정이었습니다. 인프라 담당에게 모델·기록 서버 구성을 요청하고 실제 동작을 확인했습니다. 반영 때는 백업과 되돌리기 준비, 평가 게이트, 첫 동기화와 화면 확인을 거쳐 승인했습니다. Python을 직접 구현하는 대신 요구사항과 결과를 판단하는 역할을 맡았습니다.

## 지금 상태와 다음 단계

현재는 **사내 파일럿 운영 중 · 전사 오픈 전**입니다. 자동 수집, 권한 필터, 평가 게이트, 코드 RAG와 기록 추적이 동작합니다. 다만 초기 팀원 질문 이후의 기록은 개발·시험 질문이므로 실사용 검증이 충분하다고 보지는 않습니다.

다음 순서는 **전용 서버(HTTPS) 이전 → 실사용자 시험 → 사내 오픈**입니다. 서버 이전에 맞춰 접속 보안 과제를 해결하고 운영 서버 연결의 팀 공개 조건을 확인합니다. 실사용 질문으로 평가셋을 보강한 뒤 다른 프로젝트로 넓힐 예정입니다. 전사 확대 전에는 Langfuse 본문 기록을 끄고 설치 앱 배포 준비를 마칩니다.
